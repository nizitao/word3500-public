## 1. 背景与目标

### 1.1 背景

当前系统已具备「查词 / 背词 / 测词 / 收藏」的完整基础链路，但缺少**学习过程的可视化与激励体系**：用户学了多少、坚持了多久、哪类词薄弱、哪些该复习，都没有直观反馈。学习行为无法沉淀为长期习惯。

### 1.2 目标

新增七个统计与激励模块，外加分册维度与后期模块「一起背」，并重构底部导航为四个主入口（原方案的「商城」已于 v1.3 移除）：

| # | 模块 | 一句话目标 |
|---|---|---|
| 1 | 每日打卡 | 让「今天学了吗」有一个明确状态 |
| 2 | 连续天数徽章 | 用连续记录驱动长期留存 |
| 3 | 学习日历 | 把坚持可视化 |
| 4 | 掌握率折线图 | 展示长期进步趋势 |
| 5 | 词类分析 | 指出薄弱词性，导向行动 |
| 6 | 复习面板 | 把统计结果变成待办队列 |
| 7 | 用户排行榜 | 提供社交激励 |
| 8 | 分册 / 单元维度 | 按教材进度查看掌握情况 |
| 9 | 一起背 | 组队进度（后期）；~~商城~~ v1.3 已移除 |

### 1.3 非目标（本期不做）

- 不做实时对战、语音评测、AI 出题。
- 不引入任何第三方 JS 库或图表库（全站零依赖是现有架构红线）。
- **不把 `master` 升级为多级熟练度**：仍为布尔值，仅把判定位置从客户端移到服务端（见 §4.5）。

## 3. 总体架构

### 3.1 设计原则：单一事实来源

所有统计模块**不各自记账**，统一从一条追加型「学习事件流」派生，从根本上避免各页面数字互相矛盾。

```
        学习行为（学词 / 测词 / 复习 / 自检）
                      │  客户端只上报 (word_id, action, result)
                      ▼
            study_events   追加型事件流·唯一事实来源（只增不改）
                      │
        ┌─────────────┴──────────────┐
        ▼                            ▼
  daily_stats                 learn_progress
  （按本地日聚合，              （服务端派生：
    含 mastered/learned 快照）    seen/correct/master/next_review_at）
        │                            │
        ├─► 打卡 / 连续天数           ├─► 掌握率分子
        ├─► 徽章                      ├─► 复习面板
        ├─► 学习日历                  ├─► 词类分析（JOIN words.pos）
        ├─► 掌握率折线                └─► 分册 / 单元统计
        └─► 排行榜（区间 SUM）
                      │
              points_ledger ──► （原商城兑换，v1.3 移除）
```

### 3.2 为什么分「事件流」与「状态表」

| | `study_events` | `learn_progress` |
|---|---|---|
| 性质 | 历史流水，只追加 | 当前状态，被覆盖 |
| 由谁写 | 客户端上报 + 服务端校验 | **仅服务端**派生写入 |
| 回答 | 「哪天学了什么、对错如何」 | 「这个词现在掌握了吗」 |
| 服务模块 | 打卡 / 日历 / 折线 / 排行榜 | 掌握率 / 复习 / 词类 / 分册 |

两者职责不可混用：用状态表算历史必然失真，用事件流实时算掌握率则每次都要全量重算。

**关键推论**：既然 `master` 由服务端计算，则 `seen` / `correct` 也必须服务端权威——否则客户端伪造 `seen`/`correct` 即可间接伪造 `master`。这是 §4.5 的核心。

## 4. 数据模型

新增表全部建在 `data/words.db`（与 `learn_progress` 同库，便于事务一致性）。

### 4.1 新增表

```sql
-- 1) 学习事件流：唯一事实来源
CREATE TABLE IF NOT EXISTS study_events (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id  INTEGER NOT NULL,
    word_id  INTEGER NOT NULL,
    action   TEXT    NOT NULL,        -- learn | quiz | review | selfcheck
    result   INTEGER DEFAULT 0,       -- 1 正确 / 0 错误 / -1 仅浏览
    day      TEXT    NOT NULL,        -- 本地日 YYYY-MM-DD，写入时固化
    ts       TEXT    NOT NULL,        -- UTC 时间戳
    pos      TEXT    DEFAULT '',      -- 冗余词性快照，词类统计免 JOIN
    book     INTEGER DEFAULT NULL,    -- 冗余分册快照，分册统计免 JOIN
    uid      TEXT    NOT NULL         -- 客户端批次 UUID，用于幂等去重
);
CREATE INDEX IF NOT EXISTS idx_se_user_day  ON study_events(user_id, day);
CREATE INDEX IF NOT EXISTS idx_se_user_word ON study_events(user_id, word_id);
CREATE UNIQUE INDEX IF NOT EXISTS idx_se_uid ON study_events(user_id, uid);

-- 2) 每日聚合：日历 / 折线 / 排行榜的读优化层
CREATE TABLE IF NOT EXISTS daily_stats (
    user_id        INTEGER NOT NULL,
    day            TEXT    NOT NULL,
    new_words      INTEGER DEFAULT 0,   -- 当日首次学习的词数
    reviewed       INTEGER DEFAULT 0,   -- 当日复习词数
    answered       INTEGER DEFAULT 0,   -- 当日答题数
    correct        INTEGER DEFAULT 0,   -- 当日答对数
    learned_total  INTEGER DEFAULT 0,   -- 当日结束时累计已学词数（掌握率分母）
    mastered_total INTEGER DEFAULT 0,   -- 当日结束时累计掌握数（折线数据点）
    checked_in     INTEGER DEFAULT 0,   -- 是否达成打卡
    makeup         INTEGER DEFAULT 0,   -- 是否补签
    PRIMARY KEY (user_id, day)
);

-- 3) 徽章解锁记录（徽章定义放前端常量，便于调整文案）
CREATE TABLE IF NOT EXISTS user_badges (
    user_id     INTEGER NOT NULL,
    badge_id    TEXT    NOT NULL,     -- streak_7 / master_500 / hours_10 ...
    unlocked_at TEXT    DEFAULT (datetime('now')),
    PRIMARY KEY (user_id, badge_id)
);

-- 4) 积分流水（原商城前置；商城 v1.3 移除，流水仅用于展示积分）
CREATE TABLE IF NOT EXISTS points_ledger (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    delta   INTEGER NOT NULL,         -- 正数得分，负数兑换扣减
    reason  TEXT,                     -- checkin / first_study / streak_7 / redeem_xxx
    day     TEXT,
    ts      TEXT DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_pl_user ON points_ledger(user_id, ts);
```

> `daily_stats` 必须同时存 `learned_total` 的原因：**决策 D2 把分母改成了已学词数**，分母随学习增长而变。只存分子无法回溯历史比率，折线图会算不出来。

### 4.2 对现有表的最小改动

```sql
-- 词性回填：支撑词类分析
ALTER TABLE words ADD COLUMN pos TEXT DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_words_pos ON words(pos);

-- 复习调度：支撑复习面板
ALTER TABLE learn_progress ADD COLUMN next_review_at TEXT DEFAULT NULL;
```

> 已实测确认：样本库 `words` 现有列为 `id/word/pronunciation/meaning/star/book/unit`（无 `pos`）；`learn_progress` 现有列为 `user_id/word_id/seen/correct/master/updated_at`（无 `next_review_at`）。两处 ALTER 均为纯新增列，不影响现有读写。迁移须写成幂等脚本（`PRAGMA table_info` 判断列是否存在），服务启动时执行。

### 4.3 词性解析映射（覆盖率 96.27%）

样本库 `meaning` 前缀格式**远比基础词表复杂**，存在 4 类变体，解析器必须全部覆盖：

| 变体 | 实例 |
|---|---|
| 单前缀 | `n. 天气`、`adj. 晴朗的` |
| 复合前缀 | `vi.&v. 到达`、`vt.&v. 使…`、`n.& v.` |
| 中文前缀 | `短语. 适应`、`短语. 属于` |
| 带噪字符 | `* n. 英国`、`r adv. 在后…`、`(用于否定句)也` |

**主词性归并结果**（合计 5093）：

| 归并类目 | 数量 | 占比 |
|---|---|---|
| `n` 名词 | 2853 | 56.0% |
| `adj` 形容词 | 826 | 16.2% |
| `v` 动词（vt/vi/v 合并） | 752 | 14.8% |
| `other` 无标注 | 190 | 3.7% |
| `adv` 副词 | 178 | 3.5% |
| `phr` 短语 | 105 | 2.1% |
| `pron` 代词 | 53 | 1.0% |
| `prep` 介词 | 44 | 0.9% |
| `num` 数词 | 42 | 0.8% |
| `abbr` 缩写 | 13 | 0.3% |
| `interj` 感叹词 | 13 | 0.3% |
| `art` 冠词 | 2 | 0.0% |

**图表展示归并为 10 类**（小类合并以保证可读性）：

| 图表类目 | 数量 |
|---|---|
| 名词 | 2853 |
| 形容词 | 826 |
| 动词 | 752 |
| 其他（other 190 + abbr 13 + interj 13 + art 2） | 218 |
| 副词 | 178 |
| 短语 | 105 |
| 代词 | 53 |
| 介词 | 44 |
| 数词 | 42 |
| 连词 | 22 |

要点：
- 复合前缀取**首个命中**词性作主类目，优先级 `phr > n > v > adj > adv > pron > prep > conj > num > interj > art > aux > abbr`，避免兼类词在多类重复计数导致总和超出词库量。
- `vt` / `vi` 归并为 `v`；如需细分可另存 `pos_raw` 保留原始 token 串。
- 匹配失败写入 `other`，**不写空串**，避免统计出现 NULL 分支。
- 剩余 190 条确认为**纯中文短语 / 专有名词**（「第一手；亲自」「剑桥（英国城市）」「布尼奥尔（西班牙小镇）」），本身无词性标注，归 `other` 合理。

### 4.4 迁移与回填顺序

1. **备份（不可省略）**：`sqlite3 words.db ".backup 'words.db.bak-<时间戳>'"`，`users.db` 同样备份并回读校验行数。服务运行中**不可用 `cp`**，可能拿到不一致快照。
2. 建 4 张新表 + 2 个新列 + 索引（幂等）。
3. 回填 `words.pos`（一次性，5093 行）。
4. 按 §4.5 规则重算 `learn_progress` 现有 40 行的 `master`，与旧值比对；**若出现翻转须记录并人工确认**（正常情况应为 0 翻转）。
5. 上线首日回填 `daily_stats` 基线（当日 `learned_total` / `mastered_total`），否则折线历史段为空。
6. 校验：
   - `SELECT COUNT(*) FROM words` 必须为 **5093**（迁移不得改变词条数）；
   - `SELECT COUNT(*) FROM words WHERE pos IS NULL OR pos=''` 必须为 **0**；
   - `SELECT SUM(1) FROM words GROUP BY pos` 各组合计必须为 5093。

### 4.5 掌握判定下沉服务端（决策 D1）

**本期安全性最关键的一项改动。**

现状缺陷：`web/js/quiz.js:111` 在前端算 `p.master = p.correct >= 3 && p.correct / p.seen >= 0.8`，再把 `master` 连同 `seen`/`correct` 一起 POST 给 `/api/learn/progress`，而 `server.py` 仅**原样落库**。任何客户端改一行 JS 就能把全部词标记为已掌握，排行榜与徽章立即失真。

**改造后的职责划分**：

| 角色 | 允许做的事 |
|---|---|
| 客户端 | 只上报 `(word_id, action, result, day, ts, uid)` 事件；可本地缓存进度用于离线展示 |
| 服务端 | 累加 `seen`/`correct`；**计算 `master`**；计算 `next_review_at`；写 `daily_stats` |

**判定规则（沿用现有阈值，避免历史翻转）**：

```python
def compute_master(seen: int, correct: int) -> int:
    """与前端既有规则完全一致：>=3 次答对且正确率 >=80%。
    correct<=seen 恒成立，故无需额外判断 seen>=3。"""
    if seen <= 0:
        return 0
    return 1 if (correct >= 3 and correct / seen >= 0.8) else 0
```

**实现要点**：

1. 新增 `/api/study/events` 为**唯一写入入口**，服务端在同一事务内：
   - 按 `uid` 幂等去重（防重复提交、防网络重试重复计数）
   - `INSERT study_events`
   - `UPDATE learn_progress SET seen=seen+1, correct=correct+:result`
   - 用**累加后的** `seen`/`correct` 重算 `master`（绝不采信客户端传值）
   - 重算 `next_review_at`（§5.6 规则）
2. 旧接口 `POST /api/learn/progress` **保留但降级**：
   - 仍接受请求，但**忽略** `master` 字段
   - `seen`/`correct` 取 `max(服务端值, 客户端值)`，仅用于兼容升级瞬间的本地缓存，不会因客户端传大值而虚增
   - 打 `deprecated` 日志，P2 结束后移除
3. 提供自愈工具 `POST /api/admin/rebuild-progress`：从 `study_events` 全量重算 `learn_progress`，用于任何数据漂移后修复。
4. 迁移校验：重算现有 40 行，当前 `master=1` 的 2 行应保持为 1；若翻转则说明规则或数据异常，须先排查再上线。

## 5. 功能模块设计

### 5.1 每日打卡机制

**定位**：把「今天学了没有」从模糊感知变成一个明确状态。

| 项 | 设计 |
|---|---|
| 打卡判定 | 当日 `answered >= 10` **或** `new_words >= 5` —— 要求有实质学习量，打开页面不算 |
| 写入时机 | 每次学习事件落库后，同事务 `UPSERT daily_stats` 并重算 `checked_in` |
| 日界口径 | 以**浏览器本地时区**为准，写入时固化为 `day` 列（沿用现有 `report()` 时区偏移思路），杜绝跨时区重算漂移 |
| 补签 | 每月 2 次；写入 `checked_in=1` 且 `makeup=1`；**不参与连续天数计算**，防止刷徽章 |
| 反馈 | 达成瞬间弹出「今日 +12 词 · 连续 8 天」，并预告「再答 3 题达成今日目标」 |
| 游客降级 | 游客进度不落库（现有 `server.py` 对 `_is_guest()` 返回 403），故游客端只做**本地演示态**并引导注册，不显示虚假连续天数 |

### 5.2 连续学习天数与徽章体系

**连续天数（streak）**

- 从 `daily_stats` 倒推：自今天（或昨天）向前遍历 `checked_in=1 且 makeup=0` 的连续日段。
- 宽限规则：今天尚未打卡时 streak **不清零**（当日 24:00 前有效），仅跨日未打卡才断。
- 同时统计「历史最长连续」，用于「我」页展示最佳记录。

**徽章两族**

| 族 | 阈值 |
|---|---|
| 连续族 | 3 / 7 / 14 / 30 / 60 / 100 / 365 天 |
| 累计族 | 掌握 10 / 30 / 100 / 500 / 1000 词；累计学习 10 / 50 / 100 小时 |

- 解锁检查在 `daily_stats` 更新后触发一次，`INSERT OR IGNORE` 写入 `user_badges`（幂等）。
- 徽章**一旦解锁永久保留**，后续断签不会失去——这是持久化 `user_badges` 而非纯计算的原因。
- 徽章详情页联动高亮「解锁当天的日历格子」，形成正反馈闭环。
- **阈值须按现实校准**：当前全站 `master=1` 仅 2 行，若门槛直接设 100 词将长期无人触及。建议 P2 先启用 10 / 30 / 100 三档，其余标注「即将解锁」，参数放前端常量便于调整。

### 5.3 可视化学习日历

- 月视图，每格按当日 `new_words + reviewed` 分四档色阶：`0` / `1–10` / `11–30` / `30+`。
- 点击格子 → 底部抽屉展示明细：新学 N 词、复习 M 词、正确率 X%、当日前 10 个词（取 `study_events`）。
- 补签格用**斜纹**区分，真实打卡为实色，视觉上不造假。
- 只查 `daily_stats`（单次查询取整月），不扫事件流，保证秒开。

### 5.4 词汇掌握率折线图

**决策 D2：分母 = 已学词数**

- **口径**：`掌握率 = 累计已掌握词数 ÷ 累计已学词数`（`learned = seen>0 的去重词数`）。
- 数据点：`daily_stats.mastered_total / daily_stats.learned_total`（故必须同时快照分母）。
- 交互：7 / 30 / 90 天切换；复用 `report.js` 的纯 SVG 折线（网格线 + 面积填充 + `<title>` 悬浮提示）。
- 叠加同期「新增词数」柱状，呈现投入与产出。
- 空态处理：不足 2 个数据点时展示引导文案而非空白坐标系。

**该口径的两个固有副作用，必须显式处理**

| 副作用 | 说明 | 处理 |
|---|---|---|
| **小样本虚高** | 只学 1 个词且答对 → 掌握率 100% | 分母 `< 20` 时不显示百分比，改为「已学 12 词 · 掌握 3 词」+「样本不足」徽标；折线对应区间用虚线渲染 |
| **曲线非单调** | 分母随学习增长，新学未掌握的词会拉低比率，曲线可能下跌 | 属正常且有信息量（说明在拓展新词）；图例注明「分母为累计已学词数」，tooltip 同时显示 `已掌握 / 已学` 两个绝对值 |

- 词库总量 5093 保留为**参考基准**，在页面角落另显示「词库覆盖率 = 已学 ÷ 5093」，与掌握率明确区分，避免混淆。

### 5.5 词类分析统计

- 维度：`words.pos` **10 个图表类目**（见 §4.3）。
- 指标统一为 D2 口径：`该类掌握率 = 该类已掌握 ÷ 该类已学`；并排展示「该类总词数」「已学数」作为样本量参考。
- 横向柱状图，复用 `report.js` 的 `drawHourly()` 柱状实现。
- 点击某类**下钻**到该类词表（复用 `GET /api/words`，增加 `pos` 过滤参数）。
- 自动洞察文案：「你的形容词掌握率 72%，低于整体 85%，建议加入复习队列」——把统计转化为行动。
- 样本量保护：某类已学 `< 5` 时标记「样本不足」，不参与「最薄弱类目」评选，防止 1 个词定结论。

### 5.6 复习情况统计面板

- **待复习**定义：`learn_progress` 中 `seen > 0 AND master = 0 AND next_review_at <= now`。
- 三段分布：已逾期 / 今日到期 / 未来 7 天；并列出逾期最久的 Top 10 词。
- 调度规则（简化艾宾浩斯，**由服务端计算**后写入 `next_review_at`）：

| 条件 | 下次复习间隔 |
|---|---|
| 首次答对 | +1 天 |
| 连续 2 次答对 | +3 天 |
| 连续 3 次答对 | +7 天 |
| 答错 | 重置为 +1 天，`master` 回落为 0 |

- 面板顶部主行动按钮「开始复习（N 词）」，携带队列参数跳转自检页——统计页不留「只看不做」的死角。

### 5.7 用户排行榜

**决策 D4：全员可见**

- **榜单类型**：本周学习词数（默认）/ 连续天数 / 掌握总数；支持周榜与总榜切换。
- **可见范围**：所有登录用户可见全部用户排名，不做同班 / 同组隔离。
- 数据源：`daily_stats` 按区间 `SUM` 聚合，一次查出全部名次（数据量小，无需缓存）。
- **跨库合并**：`daily_stats` 在 `words.db`、名称在 `users.db`，SQL 无法 JOIN。实现为：先聚合出 `[(user_id, score)]`，再用 `users.db` 批量查名称，**应用层内存合并**。
- **游客排除（易错点）**：游客账户的 `role` 是 **`user`** 而非 `guest`，按角色过滤会全部漏掉。必须按 **username 模式**排除：`username != 'guest' AND username NOT LIKE 'guest\_%'`，并附加 `enabled = 1`。样本库已清空现存游客账号，但 `/api/auth/guest-login` 会按需重建，**过滤逻辑不能因为「现在没有游客」而省掉**。
- **名称回退链**：`display_name → username → '用户#<id>'`。个别空的 `display_name` 虽已修复，但注册流程允许该字段为空，仍必须用 `or` 回退，不能直接取。
- **隐私红线**：不返回 email / username（当 `display_name` 可用时）；不返回逐词明细。
- **自己优先**：无论排名，底部吸底常驻「我 · 第 N 名」。
- 前三名特殊样式，其余为纯数字榜，不做复杂动画。

**冷启动现实与降级**：清理后可上榜用户仅 **12 人**，且有学习数据的仅 2 人。榜单人数 `< 3` 时不显示名次竞争，改为「已有 N 位同学开始学习，去邀请同班同学一起背」；同时**必须保证空榜不报错**（无数据的用户不参与排序，而不是显示 0 分垫底）。

### 5.8 「一起背」（P5，v1.4 已实现）

- 房间内共享词表，展示成员当日进度条与打卡状态。
- 与核心数据的关系：**只读消费** `daily_stats`，不另建进度体系，保证与单人模式口径完全一致。
- 首版只做「进度可见 + 互相点赞」，**不做实时对战**，否则复杂度失控。

**数据模型**（3 张表建在 `words.db`，与 `daily_stats` 同库以便 JOIN；成员名称仍经 `auth.list_users()` 从 `users.db` 内存合并）：

| 表 | 关键列 | 说明 |
|---|---|---|
| `study_rooms` | `code`(6 位唯一邀请码)、`name`、`owner_user_id`、`scope_book`、`scope_unit`、`max_members` | 房间与约定的共享词表范围；`scope_book=NULL` 表示全部词库 |
| `room_members` | `(room_id, user_id)` 联合主键 | 成员关系；房主退出时自动转给最早加入者，无人则解散 |
| `room_likes` | `(room_id, from_user_id, to_user_id, day)` 联合主键 | 点赞；主键即幂等键，**每人每天对同一成员限 1 次** |

**共享词表**：房间选定 `book`（1–7）与可选 `unit`，词数由 `words` 实时统计；页面「开始背这份词表」生成 `/quiz?book=N&unit=X` 深链，`quiz.js` 据此直接锁定册/单元并拉取该词表出题（空 `unit` 取整册）。不复制单词、不建房间词表，避免与 `words` 产生第二份事实来源。

**成员进度**：每人当日 `answered / new_words / reviewed / correct / checked_in` 直接取 `daily_stats`；进度条按打卡阈值取 `max(answered/10, new_words/5)`，`checked_in=1` 时置满；连续天数复用 `calc_streak()`。前端**不做二次口径计算**。

**交互与约束**：

- 创建 / 凭码加入 / 退出 / 房主解散 / 点赞；邀请链接形如 `/together?code=XXXXXX`，未加入时自动尝试加入。
- 上限：单人最多 5 个房间、单房间 30 人；页面每 15 秒轮询（页面隐藏时暂停），无 SSE、无实时对战。
- 游客：读接口返回 `guest` 演示态，写接口一律 403（游客进度本就不落库）。
- 安全：`user_id` 全部取自鉴权信息；房间内操作先校验成员关系；写操作共用 `together` 限流桶（60 次/分钟）；业务失败统一返回结构化 JSON 400。
- 隐私：成员名沿用排行榜口径（`display_name → username → 用户#id`），排除禁用 / 游客账号，不返回 email。

**验收**（2026-11-08 本地实测）：数据层离线用例全通过；HTTP 接口回归 **32/32**；Edge 浏览器 **16/16**（含 390px 无横向溢出、0 JS 异常、前端创建房间、分册单元联动、深链进入「必修第三册 · Unit 1 · 第 1/101 词」）。学习数据零改动。

## 8. 核心交互流程

### 链路 A：学 → 判定 → 打卡 → 徽章 → 日历

```
用户答一题（自检 / 训练）
  → 客户端暂存事件，800ms 防抖批量提交（复用 syncProgressServer 时机）
  → 服务端单事务内：
       ① 按 uid 幂等去重 → INSERT study_events(result, day, pos, book)
       ② UPDATE learn_progress(seen+1, correct+result)
       ③ 用累加后的 seen/correct **重算 master**（服务端权威，不采信客户端）
       ④ 重算 next_review_at
       ⑤ UPSERT daily_stats（answered/correct/new_words/reviewed + learned_total/mastered_total 快照）
       ⑥ 重算 checked_in → 阈值达成则置 1
       ⑦ 写 points_ledger
       ⑧ 检查徽章阈值 → INSERT OR IGNORE user_badges
  → 返回 { checked_in, streak, new_badges[], points_delta, mastered }
  → 前端：打卡弹层 / 徽章解锁动画 / 日历格子即时变色
```

### 链路 B：复习 → 掌握率 → 排行榜

```
复习面板「开始复习(N 词)」
  → 按 next_review_at <= now 取队列 → 跳自检页（带 queue 参数）
  → 答对：next_review_at 按间隔前移；答错：重置 +1 天且 master 回落 0
  → 达标的词计入 mastered_total 快照（同时更新 learned_total 分母）
  → 折线图当日更新；周榜下次刷新时重算
```

**一致性保障**：所有写操作以 `study_events` 插入为起点，其余各表在同一事务内更新。即使中途失败，事件流仍完整，可经 `POST /api/admin/rebuild-progress` 重算修复。

## 10. 权限与安全

| 关注点 | 处理方式 |
|---|---|
| 数据归属 | 所有 `/api/study/*` 强制以 `self._auth_user["sub"]` 作为 `user_id`，**不接受请求体传入的 user_id** |
| **掌握判定权威（D1）** | `master` / `seen` / `correct` / `next_review_at` **只由服务端计算**；客户端传入的 `master` 一律丢弃 |
| 游客 | 游客现有进度即不落库（403），统计模块对游客返回 `guest: true` 与演示态，不写入任何表 |
| 排行榜隐私 | 只输出 `display_name`（回退 username），排除 `guest` / `guest_*` 与 `enabled=0`；不返回 email / 逐词明细 |
| 房间归属（v1.4） | 所有 `/api/together/*` 的 `user_id` 取自 `_auth_user["sub"]`，不接受请求体传入；房间内操作先校验成员关系；点赞双方须为同一房间成员且不能自赞；邀请码 6 位、最多 5 房 / 30 人；写操作共用 `together` 限流桶 |
| 事件伪造 | 服务端校验 `action` 白名单、`word_id` 必须存在于 `words`、`result ∈ {-1,0,1}`、`day` 由服务端按客户端时区偏移计算而非直接采信 |
| 重复提交 | `study_events` 对 `(user_id, uid)` 建唯一索引，重复批次幂等丢弃，避免重试导致进度翻倍 |
| 刷分防护 | `checked_in` 依赖真实答题量；补签不计入 streak；`points_ledger` 单日同一 reason 仅记一次（幂等键） |
| 限流 | 上报接口沿用 `_RATE_RULES`，增设 `study_event` 桶（约 120 次/分钟，兼容自然答题节奏） |
| 回退通道 | 旧 `/api/learn/progress` 仅取 `max(服务端, 客户端)`，客户端无法通过传大值虚增进度 |

## 14. 附录：词性解析规则（v2）

```python
import re

LEAD_NOISE = re.compile(r"^[\s\*\-·•\.,;:、，。]+")
PAREN_HEAD = re.compile(r"^[\(（][^\)）]{0,20}[\)）]\s*")
TOKEN_RE   = re.compile(
    r"(?:(?:n|vt|vi|v|adj|adv|prep|conj|pron|art|num|interj|int|aux|abbr|phr)\s*\.)"
    r"|(?:短语\s*\.?)", re.I)
HEAD_RE    = re.compile(
    r"^(?:(?:(?:n|vt|vi|v|adj|adv|prep|conj|pron|art|num|interj|int|aux|abbr|phr)\s*\.)"
    r"|(?:短语\s*\.?)|[\s&/,、；;]|和)+", re.I)

MERGE    = {"vt": "v", "vi": "v", "int": "interj"}
PRIORITY = ["phr", "n", "v", "adj", "adv", "pron", "prep",
            "conj", "num", "interj", "art", "aux", "abbr"]

def parse_pos(meaning: str) -> str:
    s = LEAD_NOISE.sub("", meaning or "")
    s = PAREN_HEAD.sub("", s)
    s = LEAD_NOISE.sub("", s)
    head = HEAD_RE.match(s)
    if not head or not head.group(0).strip():
        return "other"
    toks = [t.lower().rstrip(".").strip() for t in TOKEN_RE.findall(head.group(0))]
    toks = ["phr" if t.startswith("短语") else t for t in toks]
    toks = [MERGE.get(t, t) for t in toks if t]
    if not toks:
        return "other"
    return next((p for p in PRIORITY if p in toks), "other")
```

**实测性能**：5093 行全部解析 < 1 秒；覆盖率 **96.27%**（4903 命中 / 190 归 `other`）。

**验收断言**：
- `SELECT COUNT(*) FROM words` 必须为 **5093**（迁移不得改变词条数）；
- `SELECT COUNT(*) FROM words WHERE pos IS NULL OR pos=''` 必须为 **0**；
- 按 `pos` 分组计数合计必须为 **5093**；
- `master=1` 重算前后对现有 40 行应 **0 翻转**。
